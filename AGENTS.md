# billion-context-dsh — Development Specification

> **This document is the highest-priority specification. All developers (including AI Agents) MUST comply.**

## 1. Project Overview

**billion-context-dsh** is Active Context Pruning (ACP) for the [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) — model-driven context management delivered as a `CompactionEngine` backend. It is a **port/derivation** of [billion-context-pi](https://github.com/ranxianglei/billion-context-pi) (by ranxianglei, MIT); the compression core [acp-kernel](https://github.com/ranxianglei/acp-kernel) is reused verbatim.

The model decides *when* and *what* to compress — not a hard limit. Automatic policy never summarizes by itself: it only nudges.

### Tech Stack

| Category | Technology |
|---|---|
| Language | TypeScript (strict, ESM, `.ts` import suffixes) |
| Build | tsup (bundles, **inlines acp-kernel**; `@deepseek-ai/*` stays external) |

Design decisions (see docs/dsh-porting-verification.md for the full evidence):

1. **Durable surface model** — DSH has NO in-memory message rewrite hook (`llm/stream` is read-only, `deriveMessages` is a pure projection). All compression is a durable `surfaceOp: { op: 'replace' }`; originals stay in the append-only log (decompress/search rebuild from the log).
2. **Seq is the ref** — no `<acp>` tags; the nudge's range table carries surface seqs.
3. **No automatic summarization** — `compactIfNeeded` returns null; nudges are advisory, never imperative (default copy aligned with kernel/pi: efficiency note, not "suggestion, not a requirement"; the emergency tier alone says "compress now").
4. **Model-driven summaries** — the model writes the summary via `compress`; no second LLM summarization call.
5. **`acp-kernel` pinned to an exact version** (e.g. `"acp-kernel": "0.0.29"`, NEVER `^`). It is inlined by tsup; a caret range breaks reproducibility.
6. **Search trusts the kernel** — `search_context` feeds the rebuilt doc set straight to `searchBlocks` (hybrid) and surfaces the scores; the engine adds NO second-tier gate/threshold (an early BM25 no-match gate was removed after it killed 6/46 real queries — synonyms and stemmed matches that hybrid would have found). A low fuzzy-only score (≈0.3 ceiling on noise) is for the model to judge from the surfaced score, not for the engine to filter. Algorithm bugs belong in acp-kernel, never re-implemented here.
7. **Trust the kernel for EVERYTHING it owns — not just search** — every kernel-provided capability (compression, refs, token counting, status report, nudge copy, search) is used as-is, never re-implemented, worked around, or patched on our side. When the kernel misbehaves, the fix goes **upstream** (acp-kernel issue + PR), not into this repo. Our repo only owns what the kernel explicitly does NOT (see rule 9's "kernel owns the prompt/format, the engine owns the wiring", and the Pi↔DSH mapping table in docs/dsh-porting-analysis.md §3): DSH host integration (event shapes, session semantics), surface-seq id dialect (no `<acp>` tags), durability (log, ledger, region), and host-specific channel quirks (envelope wrap, reentrancy). A **temporary, labeled workaround** is allowed ONLY when an upstream fix cannot land immediately: it MUST carry an explicit `UPSTREAM:` comment naming the upstream issue/PR, be tracked in docs/dsh-porting-verification.md, and be REMOVED the moment the upstream fix is released (see rule 11). Adapter-layer work is not a workaround — it is our job. A kernel bug worked around silently is a violation.
8. **Bundle install is the zero-config path — `cordis.patch.yml` makes the plugin GLOBAL on install** — `dsh plugin add` / the plugin store (dshmarket) run the same command, which auto-layers `dsh.bundle.patch` into the profile's composition (`dsh.profile.bundles` reconciliation; bundle layers compose before the user's own `cordis.patch.yml`). The patch must therefore carry everything a user needs to go live with NO manual composition: (a) `- id: compaction-basic disabled: true` — the host root-realm auto backend would otherwise register `ctx.compaction` too (only one provider per realm may own the service name; the row is idempotent on DSH 0.1.0-rc.6+ where the web bundle already ships it), and (b) the `- insert: - id: compaction-acp name: 'billion-context-dsh'` row at the profile root (host plane = global for that profile, all modes; shipped presets keep their realm-local basic fallback). NO `config` on the bundle row: `modelContextLimit` auto-detected, out-of-box prompt copy; users who want custom config write a SAME-ID `compaction-acp` row in their own `cordis.patch.yml` (overrides the bundle row). The README's manual composition rows are the plain-`npm install` path (which touches no profile) and the customization reference — NOT a required follow-up to a store install. Contract guarded by `tests/bundle-patch.test.ts`.
9. **Pressure runs against the SUSTAINABLE input budget, not the raw window** — every provider reserves the adapter's per-request output cap (`defaultMaxTokens`) at the end of the window on each request, so a 96K window with a 16K cap carries at most 80K of input. `windowFor` (`src/index.ts`) subtracts the cap in one place (`applyReservation`); `probeModelWindow` (`src/window.ts`) returns window + cap in a single `resolveModelInfo` call and the cap is cached per route (`outputReservationCache`). The route is resolved by `routeFor`/`liveRoute` (`src/window.ts`) from the session's LIVE `request/context` event — NEVER the `agent.options` snapshot, which still names the PREVIOUS route after a mid-session model switch (the host appends `request/context` inside the same step's `buildRequest`, so the first `agent/pre-step` after a switch lags one request and then self-heals); the same pair stamps the compression provenance, so `windowFor`, the `compress` tool and `/acp compress` share ONE route source. Skipped for an explicit `modelContextLimit` (the operator owns the denominator), a failed probe (raw 128K fallback preserved), a degenerate cap ≥ window, and `autoModelContextLimit: false`. The result carries `rawLimit`/`outputReserved` so `/acp status` can show the arithmetic. See docs/output-reservation-design.md.

## 3. Hard-won rules (from v0.1.1 long-session battle)

These are NOT style preferences — each cost a live-session bug:

1. **Token estimation MUST use `defaultCountTokens`** (CJK-aware: 1 char/token for CJK, 4 chars/token otherwise) — NEVER `estimateTokensFast` (flat 4 chars/token). This is the billion-context-pi algorithm. **Exception**: the shadow price written to host events (`compaction/summary`/`compaction/prune` `shadowedTokenCount`) must NOT use `defaultCountTokens` — it must speak the host's flat-4 vocabulary (rule 12; using `defaultCountTokens` there bricked a live session, issue #54).
2. **Nudge usage MUST prefer `sessionProjections.contextPressure.projectedTokens`** (matches UI context-occupancy display, includes fixed overhead) — NEVER `.totalTokens` (request+response pressure; observed 230% vs ~20% real). Falls back to `tokenMeter.measure(session).surfaceTokens`, then `defaultCountTokens` character heuristic. Displayed percentage is capped at 100. **Nudge context breakdown MUST be re-pointed to the SURFACE** — `buildNudge` feeds the kernel the FULL log (`allLogMessages`, needed so T2/T3 distillation anchors every block), so the kernel's `computeContextBreakdown` reports HISTORICAL totals (compressed-away originals re-counted: observed `85.2K tool` in the nudge vs `8.5K tool` in `acp_status`). The engine overrides `nudge.contextBreakdown` with `computeSurfaceBreakdown(state, messages, total, growth)` (src/nudge.ts): classification mirrors the kernel (tool-call/tool-result → tool, `system` role → system, ```` ``` ```` fence → code, else text) EXCEPT summaries, which come from active-block `block.summary` (kernel detects summaries by a `[Compressed conversation section]` text prefix that DSH checkpoint nodes never carry); checkpoint summary nodes (`source.plugin === 'compact'`) are excluded from the fed messages (they are not in any block's `effectiveMessageIds` and would double-count — mirror of `/acp` status's `isCheckpointEvent`). Display-only — never drives `shouldInject`.
3. **Nudge range table MUST be computed from the surface** (`buildCompressibleSeqRanges`), NOT from kernel `compressibleRanges` — `UPSTREAM:` the kernel ref map drifts after surface replacements in long sessions, hiding large tool results and producing `end < start` ranges (labeled workaround per rule 11 — tracked in docs/dsh-porting-verification.md, revisit on the next kernel bump and drop this once the drift is fixed upstream). Ranges are ordered **oldest-first** (stable across turns — the model can consume them front-to-back without re-ranking; matches the kernel's `oldest first` list and the host's compression rhythm) and each row carries a **kernel-parity tool/text share** (`[tool X% | text Y%]`, count-based `toolPct` via `isToolEvent` — tool-call + tool-result both count as tool) so the model can spot consumed tool-heavy spans without a drilldown.
4. **Range solving is shrink-then-expand** — `resolveSurfaceRange` shrinks edges inward to balanced cuts; if that collapses (a lone tool message), it EXPANDS outward to the smallest balanced tool-call/result pair. A model compressing a single "consumed tool output" is the norm, not the error.
5. **Test fixtures MUST mirror real DSH structures** — a real tool-result block is `{ type: 'tool-result', toolCallId, content: ContentBlock[] }` (nested), NOT `{ callId, output }`. `extractText` recurses into nested `content`. A wrong fixture silently passes while production breaks (this exact mismatch hid the seq-without-ref bug).
6. **Ledger is log-rebuilt** — `rebuildBlockLedger` reads `compaction/summary` events; a `shadowedTokenCount: 0` entry is BACKFILLED from the shadowed originals in the log (legacy blocks must still report real reclaimed tokens).
7. **Stale seqs are recovered, not errors** — a compress range whose edges were shadowed by an earlier compression (old nudge table / old compress result) is remapped to the still-live content of the requested span (`recoverStaleRange` in `resolveSurfaceRange`); a fully shadowed span throws `AlreadyCompressedRangeError`, which `handleCompress` reports as "already compressed" with the covering block ids. Block checkpoint nodes are NEVER folded on a stale reference — distillation (tier 2/3) stays an explicit act on a LIVE checkpoint seq. Invented/other-session seqs (not in the log) still fail with acp_status guidance. Prompt-only guidance proved insufficient: the engine must absorb the stale reference. **Distillation is a ready-made call, not a hunt** — the nudge tier line ships the checkpoint seqs AND the exact `compress({ content: [{ startSeq, endSeq, summary }] })` params (`{firstSeq}`/`{lastSeq}` template slots), and every compress result reports its tier (`, tier N`) even for tier 1, so a distill that the range solver degraded to a plain fold is never silent (issue #60 P1).
8. **Successful compress call/result pairs MUST be hidden (DEFERRED); orphan tool messages MUST be pruned before range solving (but never in-flight calls)** — the durable summary node is written mid-turn, before the current `compress` tool/result lands, so leaving that pair visible produces `assistant(tool_calls) → user(summary) → tool(result)`, which strict providers reject with HTTP 400. `session.append` is NOT reentrant: hiding synchronously inside the `session/event` listener throws "session append cannot reenter while another append is being published" on live sessions and the dispatcher silently swallows it, so the engine defers the hide to a microtask (`deferCompressPairHide`) that drains before the agent loop resumes. Only a node carrying EXACTLY the compress call is hidden — hiding a multi-call node would orphan its siblings' results (the visible pair is position-safe on the current harness anyway). Separately, orphan tool messages corrupt the pairing balance cache and fragment large ranges: `stripOrphanedSurfaceToolMessages` prunes orphan `tool/result`s, assistant nodes whose calls all lack results, AND "broken pairs" whose result is not adjacent to the call on the surface (a compaction summary a buggy older version inserted between them — auto-heals deadlocked legacy sessions), all via the durable `compaction/prune` protocol. The strip runs before every range solve: at `agent/pre-step` UNCONDITIONALLY (a low-pressure session must not 400 on a crash orphan), inside `buildCompressibleSeqRanges`, and at the top of `handleCompress`, which protects ALL in-flight calls of the step (`openToolCallIds`), not just its own call id, so a sibling tool in the same assistant message is never pruned before its result lands. Finally, one kernel-rejected range (e.g. messages fully absorbed into an earlier block's `effectiveMessageIds` → "Range contains no compressible messages") must not poison a batch: `handleCompress` fails only when nothing landed, otherwise it lands the successful blocks and reports the failures as advisory lines.
9. **The model tool `acp_status` MUST be rendered by kernel `buildStatusReport`** (upstream-aligned CONTEXT BREAKDOWN / COMPRESSED BLOCKS) — NEVER hand-roll the breakdown format in the engine. The engine only appends the kernel nudge decision line, the DSH `Surface:` seq anchor, and — for ACTIVE blocks only — a `Checkpoint seqs` row mapping each kernel ref (`bN`) to its checkpoint summary seq (`blockRegistry` → `summarySeq`), because acp_status is blind to summary nodes (they are excluded as messages below) and the checkpoint seq is the model's ONLY route to T2/T3 distillation (issue #60 P2). Window semantics (`estimated context` / `context window` rows) stay OUT of the model tool — they are a human-side `/acp` concern. The `messages` fed to `buildStatusReport` MUST exclude checkpoint summary nodes (`source.plugin === 'compact'`), or the summary is double-counted (once as `block.summary` summaries, once as visible text). `decompress` accepts the kernel block ref (`bN`, what acp_status shows) via `blockIdOfKernelRef` — exact `/^b\d+$/` match first, compaction-id prefix fallback — so the displayed block rows are directly usable by the model. **Drilldown passes through verbatim**: `handleStatus` forwards `scope`/`view`/`tool`/`sort`/`limit` to `buildStatusReport` (all optional; no args = overview), and a drilldown request answers with the kernel report alone — no Nudge decision line (upstream mirror `if (args.scope) return base`) — while the `Surface:` anchor stays in every mode because it is the model's compressible-ref locator. **Drilldown rows are kernel refs (mN, dense log-order ids); compress ACCEPTS them** — `handleCompress` reverse-maps an mN boundary to the live surface seq via the CURRENT turn's `state.messageRefs.byRef` (CoreMessage.id = seq, or `seq#callId` → split on `#`; the ref map must come from `turn.state` after `processTurn`, never the persisted store state, because acp_status's turn is never persisted — a store-state lookup would dead-loop the model with false "unknown mN" errors). An unknown mN (never assigned on the current surface) fails with guidance; a valid mN whose span was already compressed reuses the recover-stale / already-compressed semantics (rule 7). The engine never rewrites kernel report text. **The model channel may wrap ANY tool's args under `{ arguments: {…} }`** (same double-nesting that birthed `unwrapCompressArgs`; live-verified `{"arguments":{"scope":"compressed"}}` silently rendered the overview) — `handleStatus` MUST peel the envelope (`unwrapEnvelope`, object or JSON-string forms) before passing options to `buildStatusReport`. acp_status is the ONLY all-optional tool, so the envelope passes schema validation and would drop params silently; decompress/search_context reject the envelope at the schema gate (required `blockId`/`query` missing) — a loud, correct failure, keep those properties required. Likewise the `compress` content ITEMS carry `required: true` on `startSeq`/`endSeq`/`summary` — a live session showed a model omitting `summary` pass the old no-`required` items schema and loop on the kernel's "Summary is empty" (which never names the field); the gate now fails the same call with `missing required property "content[0].summary"`. That gate only sees the model's TOP-LEVEL arguments, so a WRAPPED call (`{ arguments: { content: [...] } }`) bypassed it and the retry-loop window survived in the wrapped form — `handleCompress` therefore re-runs the SAME per-item check on the unwrapped content (`validateContentItems`, throwing the host's `ToolArgsError` so both forms share one error surface) and treats an empty/whitespace-only summary as missing. Only the TOP-LEVEL `content` stays optional: a required `content` would reject the wrapped-`{ arguments }` form before `handleCompress` can unwrap it. This is the kernel-copy principle from the config.prompts work applied to acp_status: kernel owns the prompt/format, the engine owns the wiring (docs/acp-status-align-design.md).
10. **Tool identity lives in `message.source.callId` / the nested `tool-result` block — NEVER `message.toolName`** — a real DSH `tool/result` event carries no `toolName`/`toolCallId` at the message level (39/39 live events verified). The projection backfills `toolName`/`toolCallId` from an index of assistant tool-call ids (`buildToolCallIndex` → `call.id → call.name`), keyed by the SAME `toolCallIdOfResultEvent` extractor (`block.toolCallId ?? source.callId`) that `src/region.ts` uses for call/result pairing — one shared implementation in `src/messages.ts`, never a copy. Without the backfill every tool output lands in an empty-named category: `acp_status`'s `Top tools` renders ` (62%)` and the kernel Tip line reads `tool:""`, silently hiding the true tool from the model. Test fixtures MUST use the real shape (`source.callId` + nested `tool-result` block) — a faked `message.toolName` fixture passes while production breaks (rule 5). The index is a pre-scan, so a result preceding its call still resolves, and an event with no identity stays `''` (empty name, NOT `undefined` — the kernel's `toolName ?? "text"` would mislabel it as text).
11. **Kernel defects are fixed UPSTREAM, never patched locally** — when the kernel misbehaves (ref-map drift, wrong token counts, wrong search hits, layout bugs), the fix belongs in acp-kernel: file an upstream issue, land the PR there, then bump the pin here. A local workaround is the exception, allowed ONLY when an upstream fix cannot land immediately, and then ONLY as a labeled stopgap: an explicit `UPSTREAM:` comment (naming the upstream issue/PR), a tracking row in docs/dsh-porting-verification.md, and a removal gate — the workaround MUST be deleted once the upstream fix is released (design decision 7). Silent local patches are a violation even when they work: they fork the algorithm, drift from upstream fixes, and turn this repo into a second kernel. **Current labeled workarounds**: `buildCompressibleSeqRanges` (kernel ref-map drift after surface replacements — rule 3; revisit on the next kernel bump and drop it if the drift is fixed upstream). The former second entry — `src/tool-pairing.ts`, a local mirror of `dsh-compaction`'s `toolPairingBalancedBefore/After` added for issue #124 — was REMOVED per its own removal gate (issue #136): the peer floor now guarantees dsh-session ≥ 0.1.5, whose published seam packages read events through `eventAt()`/`snapshotEvents()`, so the host helpers are imported again (guard: `tests/tool-pairing-host.test.ts`).
12. **Shadow prices MUST speak the host's token vocabulary — `defaultCountTokens` is display currency, NEVER event currency (issues #54 and #103)** — the host token-meter's `foldSurfaceProjection` consumes every `compaction/summary`/`compaction/prune` `shadowedTokenCount` as a shadow-price CLAIM against ITS OWN running total, priced with the host's flat-4 estimator (`estimateMessage`: per block `ceil(chars/4)+4`, `+4` per message, `deriveEventMessage` null → 0). The producer contract is explicit ("the counts are exact by construction: producers derive them from the same fixed estimator this module prices appends with"); the host's own `compaction-basic` complies via `this.ctx.tokenMeter.measure(session)` → `node.tokens` — exact by construction through 0.1.1, where `tokens` IS the fixed heuristic; on 0.1.2+ that same `node.tokens` read is itself the issue #103 hazard, and whether the host's compaction-basic moved to `heuristicTokens` is not verifiable from this repo (its code lives in the host web bundle, not the npm seam), so it stays an upstream follow-up. Writing claims priced with rule 1's `defaultCountTokens` (CJK 1 char/token) overdraws the meter on CJK-heavy sessions: live session `session-3aa366c3` (issue #54) had accumulated 42,076 host-tokens but claimed 74,858 → `messageTokens` went ≈ −31K → the projection schema (`zod` nonnegative) rejected every subsequent turn with "Too small: expected number to be >=0" → the session was permanently bricked, retries included. The split: rule 1 governs the engine's INTERNAL estimation (nudge percentages, ledger display, compress-result copy — keep `defaultCountTokens`); the EVENT shadow price is a separate, host-currency value. Price it with `ctx.tokenMeter.measure(session)` `nodes[seq].heuristicTokens ?? nodes[seq].tokens` for the shadowed seqs (preferred — exact by construction, follows host estimator changes automatically). The claim basis is the node's FIXED-HEURISTIC price: since DSH 0.1.2 `measure()` re-prices image nodes' `tokens` with the measured route's declared visual price (`dsh-token-meter` `route-pricing.js` `priceSurface`), while the projection ledger still accumulates appends with the fixed heuristic — summing the routed `node.tokens` overstates an image-containing range, the claim overdraws, and `messageTokens` folds negative, the same #54 brick through the image-route channel (issue #103: a screenshot session on host 0.1.2-rc.1 looped on the identical "Too small" turnError until the projection cache was zeroed by hand). `heuristicTokens` is the ledger basis on 0.1.2+; the single `tokens` field on older meters (0.1.0/0.1.1 lines) IS the fixed heuristic, so `heuristicTokens ?? tokens` covers both shapes. The meter read is wrapped in try/catch, falling back to a LOCAL MIRROR of the host's `estimateContent`/`estimateMessage` — the fallback DEFAULT must be the mirror, NEVER `defaultCountTokens` (the mirror already fixes #54; the meter is an enhancement). The mirror MUST replicate the host's edge cases line by line: null message → 0; `tool-result` with string content falls to the per-char `JSON.stringify` default branch; `JSON.stringify` operates on the host's original block object. Three event writers: `handleCompress` (src/tools.ts:419-423), `hideSurfaceSeqs` (src/region.ts:515-553 — its internal claim computation must accept a pricing parameter whose default is the mirror, since the nudge path at region.ts:773 has no ctx), `/acp compress` (src/commands.ts:88-93); the `rebuildBlockLedger` backfill (src/region.ts:422-427) stays `defaultCountTokens` — display only, never read by the host. Keep claim ↔ replace range consistency at all three write points (the host folds a claim-less replace as zero delta but THROWS on a claim/replace range mismatch). **Known co-bug to fix in the same PR**: src/commands.ts:88 calls `shadowedSeqsOf(session, startSeq, endSeq)` with the RAW edges while the transaction uses the RESOLVED `{start, end}` — when `resolveSurfaceRange` adjusts edges, `indexOf` returns −1 → garbage span → `assertProvenance` throws and `/acp compress` crashes (use the resolved edges). Regression coverage (L3, fix PR): a REAL `TokenMeter` + `SessionProjectionRegistry` end-to-end test (dsh-token-meter is a devDep; add dsh-session-projection as a direct devDep) over a step-complete CJK-heavy fixture (the real `measure` throws on step-less logs, so a new fixture is required), covering ALL three write paths, asserting `messageTokens ≥ 0` after compress and claim == host price of the shadowed span — issue #54 arithmetic (MIRROR-authoritative values, not the earlier Python approximation): b1 64,722→30,604, b2 10,054→7,836, prune 82→1,731 (fold −30,822 → +3,865, min +183). Issue #103 regression: an image-carrying fixture priced by a stub meter in the 0.1.2 node shape (`tokens` = route visual price, `heuristicTokens` = fixed heuristic — the pinned devDep has no route pricing, so the routed meter is simulated around the REAL meter's own heuristic prices) — the claim must equal the heuristic sum (== mirror == real meter price), the routed `node.tokens` sum would fold the projection negative (in-test arithmetic), and the REAL registry fold stays non-negative and agrees with the meter; plus a pre-0.1.2 single-`tokens` shape test (claim keeps reading `tokens`). Do NOT write a local fold replica as the oracle (the host fold is not importable; a self-replica proves nothing about the host not crashing). `UPSTREAM:` the host's flat-4 vocabulary undercounts CJK occupancy ~4× and its estimator is not exported — when dsh-token-meter exports `estimateContent`/`estimateMessage` (or changes the estimator), drop the mirror and diff against `meter.estimateMessage`; tracked in docs/dsh-porting-verification.md.
13. **Session replace protocol is strict and version-bound — emit ONE dialect, floor the peer range (issue #136)** — dsh-session validates every replace `surfaceOp` against EXACTLY three keys, and the key names changed across lines: ≤0.1.3-alpha.2 wants `{ op, start, end }`, ≥0.1.5-alpha.1 wants `{ op, startSeq, endSeq }`. Dual emission is impossible (a four-key op fails both validators), so the engine emits the current dialect only — every emitter (`runCompactionTransaction`, both `hideSurfaceSeqs` variants in `src/region.ts`) writes `{ op: 'replace', startSeq, endSeq }` — and the peer range floors at the first line that speaks it: `>=0.1.5-alpha.1 <0.1.6-0` (explicit bounds, never a caret, so an unverified next line is never silently admitted; pinned by `tests/peer-range.test.ts`). Older DSH (< 0.1.5) rejects every compress at runtime; upgrading the host is the only path back. Two more 0.1.5 breaks shaped the engine: (a) assistant/message embeds its provider stream and CANNOT carry `sourceEventSeqs` (runtime throw), so an invisible prune tombstone no longer exists — `hideSurfaceSeqs` writes a VISIBLE user-message carrying `PRUNE_NOTE` ('(removed by context management)'), and `buildCompressibleSeqRanges`' last-user-protection scan skips those tombstones (the local `isPruneTombstone` predicate is gone — `isRealUserTurn` / `classifySurfaceEvent`, rule 16, subsume it so ONE classifier decides who wins the protection window); (b) the host appends its system prompt as surface node 0 (`system/message`) and protects node 0 from any non-system replace ("surface replace: node 0 holds the system prompt…") — `isSystemNode` keeps such nodes out of the compressible table and out of stale-range recovery. All three pins run against REAL dsh-session 0.1.5 sessions in `tests/surfaceop-dialect.test.ts`.

14. **The search path is snapshot-cached — the ledger is O(N+B) per snapshot, the corpus is built once per snapshot (issue #133)** — `rebuildBlockLedger` (src/region.ts) builds a single-pass `compactionId → checkpoint seq` index (`summarySeqIndex`); the old per-block `summarySeqOfCompaction` full scan made it O(B·N), and `buildSearchDocs` (src/tools.ts) ran the ledger (B+1) times per search — ≈5.8B event iterations per call at B=190/N=160K (live: 20.8 min per search at 190 blocks / 13.3M shadowed tokens, issue #133). The ledger is memoized in a `WeakMap` keyed on the append-only snapshot array (identity + length check) — sound on the current seam because `sessionEventsOf(session)` returns the SAME frozen array for an unchanged snapshot and a fresh one after every append (verified against real 0.1.5 sessions). `buildSearchDocs` caches the `SearchDoc[]` corpus the same way (exported for tests/search-perf.test.ts; public API unchanged). The engine constructor calls the kernel's `setDocCacheCap(128 * 1024 * 1024)` (public tuning API — NOT a workaround, like the engine's lower nudge thresholds): the kernel's default cap is 8MB of SOURCE chars, which covers only ~11% of the largest reported session (70MB of shadowed text), so every search re-tokenizes the whole corpus (measured 18 s/call on a 40MB corpus, cold and warm identical). The cap CANNOT be tuned down instead — the kernel evicts FIFO and bills source chars only, so any cap below the corpus caches nothing (measured on a 2M-char corpus: cap = half the corpus → 1.1× on a repeat scan, cap = full → ~1000×): the only lever is the corpus size, and a lower cap would silently disable the fix for exactly the sessions it targets. **Measured cost (2M-char corpora, forced GC, corpus excluded — supersedes the earlier "~4–6.3× / worst ≈800MB" estimate)**: an entry's retained feature heap is 1.9×–48.9× its billed source chars, driven by lexical diversity — latin prose 1.9×, CJK prose 9.3×, high-entropy latin (code/logs/JSON) 26.4×, high-entropy CJK 48.9× — so 128MB ⇒ ~270MB–6.5GB, ≈0.7–1.7GB once the 70MB corpus above is cached. Accepted for a single-user host that already holds a log of that scale; the root cause (a source-char cap cannot bound a diversity-driven heap) is upstream, tracked on acp-kernel#227 (where these measurements answer the maintainer's open cap-design question — LRU does NOT help a host whose corpus exceeds the cap, since every search touches every doc). Do NOT re-open "hash the `grams` bigrams to numbers to shrink an entry" without measuring: `Set<2-char string>` and `Set<number>` both cost 20.7 B/element (measured), so the bigram container is not the lever. `decompress`/distillation paths benefit too (same ledger). **Known kernel bug (upstream, not fixed here)**: `hybridAlgorithm.score` normalizes with `Math.max(...scores)` — a hard `RangeError` crash at ~125K+ docs (V8 argument limit; reproduced at 160K docs) → ranxianglei/acp-kernel#227 + PR #228; bump the pin when it lands. Regression: tests/search-perf.test.ts (verified to fail on the old code).
15. **Block-ledger fields ride in `rawOutput`, NEVER as top-level `compaction/summary` members (issue #141)** — the frozen released-v0 reader (`@deepseek-ai/dsh-session-format-v0-to-v1`) validates every `compaction/summary` payload against an EXACT member allow-list and throws on the first non-admitted member, so writing `tier`/`kernelBlockId`/`topic`/`parentBlockIds`/`directMessageIds`/`effectiveMessageIds` as top-level members bricked every pre-upgrade v0 session log the moment the host switched to that reader. The fix (`src/block-ledger.ts` `encodeAcpBlockLedger` / `decodeAcpBlockLedger`) embeds those six fields as ONE namespaced JSON text block inside the already-admitted optional `rawOutput` member — marker `$dshAcpBlockLedger`, version `1`, empty fields omitted. Decode is strict on marker/version but lenient per-field and NEVER throws (unknown/absent marker or a future version ⇒ `{}` ⇒ tier-1 fallback), because old files and future generations must degrade, not brick. The read path (`rebuildBlockLedger`) prefers the embedded payload and falls back to legacy top-level members so in-flight sessions keep their tier/lineage across the upgrade. Regression guard: `tests/block-ledger.test.ts` feeds a real engine-written event through the codec's own `assertReleasedEventPayload(…, 0)` (must pass) and re-adds one top-level field (must throw `unexpected member`). The owner's offline recovery normalizer reuses `encodeAcpBlockLedger` so rescued files match live writes exactly (no shape drift).
16. **Injected instruction rows are compress→re-inject LOOP FUEL — the range table must barrier them, and "last user message" protection must be a REAL turn (issue #71 PR1)** — the host re-injects the CURRENT copy of an instruction file (AGENTS.md; audited shapes: `kind:'agent-instructions'` with `changes:[{action,scope,path,digest}]`, legacy `kind:'plugin'+plugin:'agent-instructions'`) the moment it disappears from the surface, so folding the current copy into a block makes its tokens come straight back and a model that keeps compressing them loops forever (live-measured: 20 of 43 compressions in a long session re-triggered an injection within 7 events; reproduced live in session-8c15904e, seq 8 absorbed by a compress → host re-injected at seq 53191). Three parts in `buildCompressibleSeqRanges` (src/region.ts): (a) `classifySurfaceEvent` (src/messages.ts: real/metadata/checkpoint/instruction; unknown plugin rows fall to instruction CONSERVATIVELY — a future host injection must never silently become compressible) gates the scope loop: instruction rows flush the open segment and are never offered; (b) the newest instruction row per scope (`source.changes[].scope` = one file; each worktree is its own scope) is pinned via `newestInstructionSeqsOf` — belt-and-braces; `guardedSurfaceSeqsOf` (that same set, surface-visible rows only) feeds the compress tool's HARD REJECT (`guardedRowsInSpan` + `protectedRowRejectionNote`, src/tools.ts: the range must be cut around current rows, and the note names the compressible slices left in the span so the model re-cuts instead of retrying the same call — the probe is POSITIONAL: it intersects the guarded set with the span the transaction will actually shadow (`shadowedSeqsOf`), never a numeric `start <= seq <= end` interval, because after earlier replacements the surface is locally non-monotonic (a checkpoint spliced ahead of older residual nodes), so a tier-2 distill of two checkpoints can carry a CURRENT instruction row numerically inside its edges while the sliced span excludes it — the interval form rejected exactly the call the nudge hands the model (issue #71 review B1); supersedes the F7 warn-only draft — the owner reversed it during PR1 review because compressing a CURRENT row has NO legitimate outcome: the host re-injects the newest copy unconditionally, so the tokens come straight back, and the reject keeps the manual path consistent with the system-side GC's iron rule "never clear a group's newest row". STALE copies stay compressible — removing them while the newest stays visible triggers no re-injection. A row without `changes[]` (legacy shape) is SKIPPED by `newestInstructionSeqsOf`: with no scope the host's presence gate cannot identify the file, so such a row can never come back and must not be guarded — guarding it turned every span over it into a permanent hard reject (issue #71 review S3; the range table still barriers it). The human `/acp compress` command gets the SAME hard reject (src/commands.ts, same two helpers from src/tools.ts): explicit intent does not override the arithmetic — the host re-injects the newest copy unconditionally, so NO caller, human or model, can legitimately reclaim anything by folding a current row (the owner extended the gate to the human path right after the tool-side reject landed, closing the "explicit human intent" carve-out); (c) the protected tail scan must use `isRealUserTurn` — the old `user/message && !isCheckpointNode` scan protected the injected row itself (the last user/message on a live surface is frequently the AGENTS.md copy the host appended in the same enter batch as the user input) while leaving the REAL last user message compressible. Engine-authored metadata rows (nudge echo, compress-pair stub) stay foldable like main (F4 classifier narrowing — guarded = `isAgentInstructionsRow && newest` only); host CONTENT rows that are not the user speaking (`@deepseek-ai/dsh-system-prompt` dynamic-context snapshot, `user-approval`, `tools-ptc`) are real content too and stay foldable — the earlier shape filed every `plugin` row as a policy barrier, which silently disabled folding there (issue #71 review B2), while unknown plugin names still fall to instruction. Stale copies are barriers in PR1 too; the system-side GC that removes them is PR2 (scope-keyed; two iron rules: never clear a group's newest row, never clear a row without a source marker). **Merge note (renumbered 13→16: main has since taken 13/14/15)**: `isRealUserTurn` subsumes the narrower guards this scan carried on main — checkpoints are their own class, and engine-authored rows (the prune tombstone written by `hideSurfaceSeqs`, the compress-pair stub) classify as `metadata`, so the local `isPruneTombstone` helper was deleted to keep ONE classifier.

17. **Model-written summaries are framed ONCE at creation, verifiedReadings ride the rawOutput ledger and MUST stay readable, and nudges stay slim (PR #132)** — three coupled durability/readability rules: (a) **Summary source framing** — model-written compression summaries carry obligation-like sentences distilled from compressed user messages, and a model executing them as if they were current user words lets stale secondhand directives drive behavior; therefore every summary is prefixed with `SUMMARY_FRAME_PREFIX` (`'[Model-written summary — not user words; re-verify any obligations before relying on them]'`, src/messages.ts — ENGLISH, because tool output speaks the English vocabulary; a localized marker would need the whole table localized, not one string) EXACTLY ONCE at creation in `runCompactionTransaction` (src/region.ts): `framedSummary = prefixSummaryBlocks(input.summary)` is written IDENTICALLY into the `compaction/summary` event's `summary` field AND its checkpoint node's content — event/node divergence would split the decompress header from the projected text. The projection-time framing in `projectEvent` is IDEMPOTENT (`withSummaryFramePrefix`) and exists only as a safety net for legacy blocks created before this release. The checkpoint predicate is `isCheckpointNode` (`user/message` && `source?.plugin === 'compact'`) — no second private predicate. Real user frames (`source.kind === 'user'`) are NEVER framed; the decompress header echoes the frame (tests/tools.test.ts M3 pins it). (b) **verifiedReadings ride the ledger, never the top level** — `compress` accepts optional `verifiedReadings: string[]` per range (files/sections actually read and checked); it persists ONLY as the seventh field of the rawOutput ledger payload (`encodeAcpBlockLedger`, src/block-ledger.ts, omitted when empty) — NEVER as a top-level `compaction/summary` member (rule 15 / issue #141: the frozen v0 reader validates an EXACT member allow-list and bricks pre-upgrade logs on unknown members). Read face: `verifiedReadingsOf(event)` (src/region.ts) = decode-embedded ?? legacy top-level, `Array.isArray` guarded, NEVER throws (`[]` on non-summary events); `rebuildBlockLedger` surfaces it on `AcpBlockLedgerEntry`. A durable datum nobody reads is pure liability, so the compress result echoes it per landed block (`, verified: <a; b>`, non-empty only, src/tools.ts `handleCompress`). (c) **Slim nudges** — the four guidance sections (`COMPRESS_PHILOSOPHY` / `HOW_TO_COMPRESS_RULES` / `TIER2_DISTILL_RULES` / `TIER3_CONDENSE_RULES`) already live in the system prompt once; repeating them in every nudge body is pure waste, so `stripNudgeGuidance` (src/nudge.ts) removes them from nudge text on BOTH the kernel default path (`adaptKernelNudgeToSeq`) and the template path (`renderNudgeFromTemplates` — host-overridden slots included); measured body ≈224B ≤ 300 budget. Nudge tests pin substrings of REAL rendered output (trigger frame present, `Context breakdown:` present, guidance absent) — never "build input from the constants, assert the constants were removed" tautologies. **B2 (unchanged-injection elision) was deliberately DROPPED** after the maintainer review: no host channel re-injects while an identical copy stays visible (dsh-agent-loop `RuntimeContextProjection` retained-check `if (this.retained?.text === snapshot) return;`; agent-instructions presence gate per rule 16's live audit; the author's own live audit recorded 0 bytes saved and 2 content losses) — zero savings by construction; the spread-stub kept `source.changes[].scope` (the v0 reader validates exactly `{kind:'agent-instructions', form:'instructions', changes[]}`), so the stub would steal #93's newest-row pin via `newestInstructionSeqsOf` while the FULL copy became a compressible stale row → content loss with no re-injection; and the `DEDUPE_SOURCES` whitelist matched at most one real frame kind (`skill-catalog`/`runtime` kinds exist nowhere in the npm seam; real runtime-context frames carry `kind:'plugin'` + `plugin:'@deepseek-ai/dsh-system-prompt'`). If a future host genuinely re-injects over visible copies, redesign against the real shapes then (stub must NOT carry `changes[]` identity and must classify as engine metadata, not instruction). Full evidence: docs/injection-governance-design.md.

- Keep `@deepseek-ai/*` devDeps on the **0.1.5 line** (pinned `0.1.5-rc.1`) and the four-seam **peer** range on the explicit interval `>=0.1.5-alpha.1 <0.1.6-0` — exactly the 0.1.5 line (every prerelease plus the final release; node-semver sorts `0.1.6-0` ahead of any `0.1.6-x` prerelease, so the next line stays rejected until it is verified and admitted deliberately). The baseline moved here on a BREAKING seam change, not a seamless bump (issue #136): the session replace-op dialect was renamed (`start/end` → `startSeq/endSeq`) under strict exactly-three-key validation, so the engine emits one dialect and hosts below the floor cannot run it — keeping the old test baseline would make the suite lie about what ships. When the next seam line lands: verify its API against docs/dsh-porting-verification.md first, widen the interval only if verified, move the devDep baseline, and re-pin `tests/peer-range.test.ts` (it asserts the whole current line is accepted and every older/newer line rejected). Every package in the dependency+peer closure must therefore be an **explicit devDep pinned to the 0.1.5 line** (currently 12 additions on top of the engine's own seam devDeps; `dsh-token-meter` pinned exactly so the harness baseline is reproducible). Re-derive the closure whenever a host package is added or dropped; the verification procedure (registry BFS + `package-lock.json` purity check) is documented in docs/e2e-harness-design.md.
- **Git worktrees MUST be created inside `worktrees/`** in the project root (e.g. `git worktree add worktrees/<branch> <branch>`). The `worktrees/` directory is gitignored and never pushed. Never create worktrees outside the project.
- **Docs must stay in sync with every PR** — before opening a PR, review the diff against the documentation: any behavior the change alters must match what the docs describe, and docs that state the old behavior must be updated in the same PR. A PR that changes behavior without touching docs is incomplete.
- **Feature work MUST document itself** — every feature (any behavior addition or change) must add an explanation of the new capability in the relevant docs: user-facing config/options in `README.md` / `README.en.md`, install-time composition options in `docs/INSTALL.md`, design decisions in `docs/*-design.md`, and the module map / hard-won rules in `AGENTS.md` itself. Precedent: the `config.prompts` feature shipped its README section, INSTALL note, config table row, and design doc in the same PR.

### Plain-language writing (all human-facing text)

Every piece of human-facing text — PR titles, PR descriptions, commit messages, code comments, docs — is written for a reader seeing it for the first time: no jargon, no private shorthand. If it can't be grasped in ~10 seconds by someone who has never seen the project, rewrite it.

- **PR title**: one sentence saying what changed and what problem it fixes, phrased like you'd tell a teammate (it becomes the main-branch commit via squash).
- **PR description**: organized as problem → cause → fix → verification; assume the reader doesn't know internal terms or abbreviations.
- **Code comments**: explain WHY (background, the trap, the premise) — never restate what the code does.
- **Commit messages**: plain-language subject; add a body only when there's background worth keeping.
- **Plain ≠ lossy**: rewriting for readability never means deleting the precise anchors — function names, variable names, parameter names, file paths, and line numbers stay verbatim. They are the grep-able evidence; the rewrite reshapes the narrative, not the substance (lesson: issue #46 v1 over-deleted `collectVisible`/dist line numbers/the options table — the user caught it and it had to be restored).

### Commit messages

The convention applies to the **squash-merge subject on main**, which IS the PR title (main is branch-protected; see §5). **Commits inside a PR are free-form** — only the final squash subject is constrained. Single-line subject, prefix by change kind (the description after the prefix is free-form, keep it informative):

- `(feat) <summary>` — feature work (e.g. `(feat) tier-2/3 block distillation — …`)
- `(fix) <summary>` — bug fixes
- `(refactor) <summary>` — internal restructuring without behavior change
- `(test) <summary>` — tests only
- `(chore) <summary>` — tooling / process (CI, deps, scripts)
- `docs: <summary>` — documentation only (README, docs/, AGENTS.md)
- `release vX.Y.Z` — the release commit, exactly as in §5 (unchanged)

The PR title is enforced by CI (`.github/workflows/pr-lint.yml` → `scripts/check-pr-title.mjs`), since a squash merge turns it into the main-branch commit (e.g. `(feat) guide multi-segment batch compress + regression test`). Contributor guidance lives in CONTRIBUTING.md. PR merges stay human-only (§5).

## 4b. acp-kernel upgrade policy (the kernel WILL move on)

`acp-kernel` is pinned **exactly** (e.g. `0.0.29`, never `^`) because tsup inlines it — a caret range makes the resolved version drift when the lockfile regenerates, breaking reproducible builds. But pinning is **not** freezing: upgrades are a controlled, manual process.

**When to check:** on any feature work, or monthly — `npm view acp-kernel version`.

**Upgrade SOP (each step gates the next):**

1. `npm view acp-kernel versions` — pick the target. Read its changelog / git diff for breaking changes.
2. Watch these hot spots (kernel changes here have bit us before):
   - `defaultCountTokens` / tokenizer behavior (CJK estimation, `createBpeTokenizer`) — tests/assert 100 CJK = 100 tokens
   - `CompressionState` shape (`messageRefs`, blocks) — `state.ts`, `region.ts` read it structurally
   - ref assignment / `compressibleRanges` — we self-compute the range table as a labeled `UPSTREAM:` workaround for kernel ref-map drift (rule 3 / rule 11); on every bump CHECK whether the drift is fixed upstream — if so, DROP the workaround and use kernel `compressibleRanges` again
   - `CoreMessage` / `NudgeDecision` types — `messages.ts`, `nudge.ts`
3. Bump the exact version in `package.json`, run `npm install` (refreshes lock), then `npm run typecheck && npm test && npm run build`.
4. **The test suite is the safety net**: 189 tests cover the battle-hardened behaviors (CJK estimation, lone-tool expansion, surface range table, ledger backfill, ref-tag projection, orphan-tool pruning, broken-pair healing, deferred compress call/result hiding, in-flight call preservation, batch resilience, acp_status upstream alignment, dual-id bN decompress, tool-result toolName backfill, acp_status drilldown passthrough + mN/seq separation + checkpoint row exclusion + multi-call survival, compress accepts drilldown mN refs (mapped to live surface seqs; unknown mN fails with guidance), nudge range table tool/text share + oldest-first ordering, wrapped-`{ arguments }` envelope peel, searchBlocks hybrid retrieval: stemmed/CJK matching, shadowed-message hits, innermost tier-1 block back-link, `/acp status` nudge arbitration (read-only processTurn on a cloned state — `nudge: idle/ACTIVE — reason` + distance to the next nudge; never writes the store) + ledger listing + dual-id decompress, `/acp status` lists ALL blocks (issue #47/#48), default compress description ships the #43 semantic-timing + actionable-summary carriers (prompts test #5b), default search_context description + system prompt quick-reference ship the #44 search-first carriers (prompts test #5c), anti-over-compression carriers in the default compress description + system prompt — cite-verbatim WHEN NOT bullet, "fully consumed" qualifier, re-verify self-check — proven out via local config.prompts overrides before promotion (prompts test #5d), shadow-price host-vocabulary claims via REAL TokenMeter + SessionProjectionRegistry E2E over CJK fixtures (issue #54: compress-tool claim == meter price, prune claim == host price, /acp compress uses RESOLVED edges, projection stays non-negative, mirror edge cases, deriveEventMessage null projection; tests/shadow-price.test.ts), T2 distillation availability (issue #60: nudge tier seqs first..last compress straight into a tier-2 block end-to-end; every compress result reports its tier — `, tier 1` included, no silent downgrade), compress items-level required gate on BOTH the direct and the wrapped-`{ arguments }` form (missing `summary`/`startSeq`/`endSeq` rejected at the gate naming `content[N].<field>`; a topic-only entry names all three missing fields; a whitespace-only summary counts as missing; the wrapped OBJECT form with a FULL entry still compresses — the top-level `content` stays optional for the envelope; an empty `content: []` is a benign no-op); plus `tests/kernel-upstream/` — 36 vendored upstream acp-kernel search tests (searchBlocks/blockDocs/messageDocs role weighting, algorithm selection, CJK/fuzzy gates, async-misuse guard) migrated to the public API, see issue #30). Any kernel behavior change that breaks one of those turns red here — do NOT release on red.
5. Optionally enable new kernel features deliberately (e.g. `createBpeTokenizer()` behind a config flag) — never adopt silently.
6. Release per the workflow below (bump own version, publish, `gh release create`).

If a kernel major version breaks the seam contracts, treat it as a porting task: re-verify against docs/dsh-porting-verification.md before shipping.
